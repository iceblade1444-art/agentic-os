# Agentic OS → SaaS: полный план доработки

**Дата аудита:** 2026-08-15. Аудит покрыл четыре среза: серверное ядро и auth,
фронтенд и UX, агентная часть и интеграции, эксплуатация и безопасность.
Документ продолжает `ROADMAP_2026H2_RU.md` (продуктовые фазы) и
`PRODUCT_HARDENING_ROADMAP.md` (hardening) — здесь то, чего в них нет:
путь от «зрелый однотенантный продукт одной фабрики» до «продаваемый SaaS».

---

## 1. Вердикт одной страницей

Сегодня Agentic OS — это **качественно сделанный single-tenant продукт под одну
компанию**: один workspace на инсталляцию, один Creator из `.env`, данные в
JSON-файлах с Postgres-зеркалом, Hermes-флот прибит к одному Linux-хосту,
домен Milana Premium зашит в промпты, seed БД, CSP и клиентского бота.

Что при этом **уже есть и являет реальную продаваемую ценность**:

- **Один ассистент на 6+ поверхностях** (браузерный голос, LiveKit-звонок,
  веб-чат, личный Telegram, корпоративный мессенджер, мобильное приложение)
  с единым промптом (`assets/js/mila-prompt.js`) и честной композицией под
  доступные инструменты. Это редкость на рынке.
- **Модель прав и подтверждений агентных действий** (`server/lib/mila-actions.js`):
  personal / knowledge-read / ERP-read / operator-only, двухшаговые
  подтверждения с TTL — голос не становится боковым входом в админку.
- **Consent-first Telegram** + двухботовая архитектура (внутренний ассистент и
  клиентский фронтдеск с лидогенерацией, знающий только базу знаний).
- **`/learn`** — обучение флота навыкам словами.
- **Операционные рутины** (утренний бриф, вечерний итог, недельный ERP-обзор,
  аномалии, протоколы совещаний, recap чатов) — то, за что платят.
- **Свой speech-стек** с узбекским TTS — дифференциатор для ЦА-рынка.
- Зрелый аккаунтный слой: MFA, восстановление, self-service экспорт/удаление,
  privacy-boundaries с тестами.

Чего нет совсем: **мультитенантности** (ни одной строки про tenant/organization),
**биллинга и учёта LLM-затрат** (ни одной строки), **горизонтального
масштабирования** (in-memory anti-replay, планировщики без лидера,
Telegram-polling). Плюс найден **блокер: логин сейчас сломан на `main`** (§3.0).

## 2. Стратегия: два трека вместо одного прыжка

Переписывать всё в мультитенантную архитектуру до первого клиента — полгода без
выручки. Архитектура же прямо сейчас хорошо ложится на другую модель:

**Трек A — «Appliance» (продавать можно через 1–2 месяца).**
Одна инсталляция = один клиент: отдельная VM/контейнерный стек на компанию.
Это то, чем продукт уже является — нужно лишь вычистить хардкод Milana,
довести installer и закрыть критические дыры (Этапы 0–2). Цена — как у
enterprise-инсталляций, обслуживание — скриптами, которые уже есть
(`deploy.sh`, operations.py). Первые 3–10 клиентов живут так, финансируя трек B.

**Трек B — «Настоящий SaaS» (3–6 месяцев параллельно).**
Мультитенантное ядро: Postgres как единственный источник истины, Redis,
tenant-scoped конфигурация, self-service регистрация компании, биллинг с
метрингом токенов (Этапы 3–4). Сюда переезжают новые клиенты; appliance
остаётся премиум-предложением для тех, кому нужен on-prem (а для фабрик СНГ
on-prem — аргумент продаж, не костыль).

Дальше этапы. Оценки — в неделях работы одного разработчика с ИИ-агентами.

### 3.1 Безопасность — закрыть до первого внешнего клиента
1. **`agentos-runtime` без аутентификации + RCE.** `app.py` не проверяет ничего

   (~строка 6383) получает строки из заголовков задач. Цепочка
   «unauth HTTP → self-approve → shell» замыкается внутри docker-сети.
   Минимум: общий bearer между Node и runtime + убрать `shell=True`.
   Правильно: см. §5.4 — ужать runtime до 5 реально используемых эндпоинтов.
2. **`/rtc` — неаутентифицированный прокси** (`server/index.js:150`,
   `livekit-proxy.js:33`): смонтирован до `requireAuth`. Добавить проверку сессии.
3. **`AUTH_TOKEN` как мастер-пароль в обход MFA** (`auth.js:271, 335`) — пустой
   email + токен = вход Creator'ом без MFA и без аудита. Убрать этот путь или
   ограничить локальной сетью + логировать.
4. **`SESSION_SECRET` fallback** (`config.js:83`): без переменной подпись
   сессий = литерал `"agentic-os-dev-secret"`, и от этого же секрета выведены
   ключи шифрования MFA/governance/Google-токенов. Сделать отсутствие
   секрета фатальной ошибкой старта; версионировать ключи шифрования.
5. **Секреты интеграций в `data/db.json` открытым текстом** (`store.js`) —
   шифровать AES-256-GCM, как уже сделано для Google-токенов.
6. **Роль `Design` ломает Postgres**: CHECK-constraint в
   `postgres-migration.js:124` не знает про Design → shadow-sync падает на
   любом таком пользователе.
7. **HSTS + CSRF-токены + `Permissions-Policy`**; `/hermes/*` исключён из
   security-заголовков (`index.js:139`) — пересмотреть.

### 3.2 Данные — до первого клиента
8. **Off-site бэкапы + шифрование архивов** — ✅ сделано. Каждый бэкап

## 5. Этап 2 — Данные, масштаб, наблюдаемость (~4–6 недель, параллелится с Этапом 1)

1. **Postgres — единственный источник истины.** Сейчас «миграция» — это
   зеркало: TRUNCATE + полная переливка всех таблиц каждые 30 секунд
   (`postgres-migration.js:371–384`), `payload jsonb` вместо схемы, а планы
   записи пересобираются из JSON даже в режиме `primary`
   (`postgres-auth-write.js:160`). Для SaaS это тупик (O(N) переливка всех
   пользователей на каждую смену пароля). Нормализованная схема, точечные
   записи, миграции в `deploy.sh`; JSON остаётся только экспортным форматом.
   Перевести в Postgres и то, что сейчас живёт только в JSON: `db.json`,
   governance, messenger, telegram-links, push-devices, profiles.
2. **Redis:** сессии, rate-limit (сейчас in-memory с `hits.clear()` при 5000
   записей — атакующий обнуляет лимиты всем), anti-replay pairing-грантов и
   MFA-challenge (сейчас повторно используемы на втором инстансе), OAuth
   state, typing/online мессенджера.
3. **Планировщики и боты:** выделенный worker-процесс (или leader election) для
   reminders/briefs/digests; Telegram с long-polling на webhook — иначе второй
   инстанс = 409 Conflict и мёртвый бот.
4. **Ужать `agentos-runtime`.** Из ~112 маршрутов Node использует 5
   (orchestrator status/create, approvals, events). 7815-строчный `app.py`,
   ~80 wave-скриптов и дублирующий голосовой контур — legacy. Либо переписать
   в маленький сервис «планировщик + approvals» с bearer-auth, либо перенести
   5 вызовов в Node и удалить контейнер.
5. **Наблюдаемость:** structured-логи (pino) с request-id, `logging:` c
   `max-size` в compose (сейчас логи растут неограниченно), `/metrics`
   (Prometheus), HEALTHCHECK в Dockerfile/compose, алерты на 5xx/latency.
   Доменный мониторинг (operations.py, Four C) уже хорош — оставить.
6. **CI → CD:** деплой из CI по тегу вместо ручного `bash deploy.sh`, staging
   с реальным Postgres (кандидат-контейнер сейчас принудительно в json-режиме),
   Dependabot/Renovate, замена неподдерживаемого `http-proxy` (2020 год),
   порог покрытия.

## 6. Этап 3 — Мультитенантность (~6–10 недель)

Ядро трека B. Порядок важен: сначала данные, потом конфигурация, потом агенты.

1. **Сущность `tenant`.** `tenant_id` в каждой таблице и каждом запросе;
   Creator из env → роль owner внутри тенанта; `workspace` из синглтона
   (`onboarding.js:31`) — в коллекцию. Row-Level Security в Postgres как
   страховка от утечек между тенантами (уроки `privacy-boundaries` — та же
   логика уровнем выше: «не знать в комнате» надёжнее, чем «не говорить»).
2. **Tenant-scoped конфигурация:** интеграции, боты (у каждого тенанта свои
   Telegram-токены), промпты, локали, лимиты, KB/vault. Obsidian-vault «один
   на всех» → per-tenant каталог или БД-хранилище знаний.
3. **Self-service:** регистрация компании без участия владельца платформы,
   email-инвайты, MFA для **всех** ролей (сейчас `mfa.js:20` — только
   Creator/Admin), позже SSO/OIDC для enterprise.
4. **Агентный слой без хоста.** Hermes-флот в текущем виде (systemd --user,
   `~/.hermes`, токен регуляркой по HTML в `hermes-kanban.js:53`, PTY/shell
   через `/hermes/`-прокси) в мультитенантном SaaS не живёт. Решение:
   оркестрация переезжает на управляемый API (Claude Agent SDK / свои
   worker'ы) с изоляцией per tenant; Hermes остаётся фичей appliance-трека.
   `/hermes/`-прокси в SaaS не показывать никогда (это shell на хосте).
5. **MILA-бэкенд — в репозиторий или BYOK.** Голос и чат зависят от закрытого
   внешнего сервиса с Gemini-ключом (`server/lib/mila.js`). Для SaaS: либо
   включить его в этот репозиторий и выдавать per-tenant ключи, либо BYOK.

2. **Лимиты:** мягкие (уведомление) и жёсткие (отказ) пороги per tenant/план;
   rate-limit per tenant, не только per IP.
3. **Тарифы и оплата.** Для Узбекистана/СНГ Stripe недоступен продавцу — планировать
   **Payme/Click + инвойсы** для локальных клиентов и Paddle/LemonSqueezy

4. **BYOK** как опция плана: тенант приносит свои ключи OpenAI/Anthropic/Gemini —

| P1 | Postgres по-настоящему; Redis; worker/webhook; ужать runtime; логи/метрики; CD | оба | 4–6 нед |
| P2 | Tenant-ядро + RLS; tenant-конфиг; self-service; MFA всем; агенты без хоста; MILA-бэкенд/BYOK | B | 6–10 нед |
| P2 | Метринг + лимиты + тарифы + оплата (Payme/Click/Paddle) | B | 4–6 нед |
| P3 | Сборка фронта, PWA, аудит-лог, лендинг/прайсинг, DPA | B | фоном |

Суммарно: **appliance-трек продаваем через ~6–8 недель** (Этапы 0–1 + часть 2),
**мультитенантный SaaS — через ~4–6 месяцев** при параллельной работе.

## 10. Главные риски

1. **Зависимость от закрытого MILA-бэкенда** — единственная точка, без которой
   не работают голос, чат, Telegram-ассистент и `/learn`, и её исходников нет
   в репозитории. Решать в начале трека B, а для appliance — задокументировать
   деплой этого сервиса.
2. **Hermes** — сторонний продукт, интегрированный скрейпингом HTML и подделкой
   Origin; любой его апдейт ломает Kanban/Skills/Cron. Изолировать интеграцию
   контрактом сейчас, замещать в SaaS-треке.
3. **Тестовая слепота к рантайму** — уже вторая регрессия класса «зелёный
   suite, красный прод» (см. `agentic-os-testing-lesson`). Пока нет
   HTTP-интеграционных тестов, каждое изменение auth-слоя — рулетка.
4. **Один сервер, один диск** — до off-site бэкапов любой аппаратный отказ
   уничтожает и прод, и копии.
